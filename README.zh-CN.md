# dsh-desktop —— 把 DSH 变成桌面程序

把 dsh 的网页端装进一个 Electron 原生窗口，并且**关掉所有窗口 = 退出程序并停掉后台服务**，
不留任何后台残留；只要还有窗口在用同一个后台服务，它就不会被关掉。

> **语义变更（2026-10-10 第二版）**
> 第一版是「关闭窗口 = 隐藏到系统托盘，服务器继续跑」。实际用下来，用户关掉窗口后
> 后台的 `dsh web` 还在跑，只能自己去 `ps` 里找进程杀 —— 这正是第二版要修的问题。
> 现在不保留托盘、不保留隐藏：**关就是关**。

> **语义变更（2026-10-15 第四版）**
> 第三版支持多窗口（多个窗口共用一个后台服务），但服务器的寿命绑在「起它的那个窗口」身上：
> 关掉主窗口，副窗口正在用的服务当场消失。第四版把判据换成**「还有没有窗口在用」**：
> 主窗口关掉后服务继续跑（副窗口不受影响，新开的窗口还能接上），
> 只有最后一个窗口退出时才回收服务。详见第五、六节。

## 一、它到底做了什么

```
┌────────────────────────────────┐
│  Dsh Desktop（Electron 壳）     │
│  ┌──────────────────────────┐  │
│  │  dsh web 的网页界面       │  │  ← 窗口里加载的就是原来的 DSH UI
│  └──────────────────────────┘  │
│         │ 托管（父子进程）       │
│         ▼                       │
│  dsh web --no-open --port 0     │  ← 端口由系统分配，壳退出时一并回收
└────────────────────────────────┘
```

四个要点：

1. **自己拉起、自己回收服务器**：应用启动时用 `--port 0` 起一个专属的 `dsh web`，端口由系统挑空闲的，
   所以不会跟你手动在终端里跑的 `dsh web` 抢端口；退出时按进程组回收，不留孤儿进程。
2. **必须解析带 token 的地址**：DSH 网页端有防蹭用校验，直接访问 `127.0.0.1:<端口>` 只会拿到 401。
   服务器启动后会把唯一可用的地址（含一次性 token）打出来，桌面壳从输出里抓到这一行再加载。
   （第四版起，服务器的 stdout/stderr 直接写 `dsh-server.log`，壳改成从这个文件里读那一行 ——
   这样壳退出后服务器不会再被一根断掉的管道牵着，见第六节。）
   这也是为什么启动时会先看到一张「正在启动 DSH 服务器…」的过渡页——冷启动要装配整个 profile，实测 17~40 秒。
3. **关掉所有窗口就是退出**（第二版，第四版细化）：不再拦截 `close` 事件；关掉窗口就退出这个窗口的进程，
   后台服务则在**最后一个窗口退出时**回收。原来托盘菜单里的功能（在浏览器打开、重启服务器、看日志、
   打开数据目录）已整体挪到应用菜单 `DSH` 下。
4. **可以开多个窗口**（第三版）：重复点击图标会再开一个窗口，加载的是**同一个地址**——
   等价于「两个浏览器窗口打开同一个页面」，不会再多起一套后台服务。
   第一个窗口自己起服务器并把地址公告到 `~/.dsh-desktop/endpoint.json`，后面的窗口读到它就接上去。
   详见第五、六节。

## 二、退出与回收：四条路径 + 一层兜底

「壳关了、后台服务还在」这件事必须从每一条件退出路径上都堵死，所以：

| 触发方式 | 走哪条路 | 结果 |
| --- | --- | --- |
| 点窗口 × / Alt+F4 / 任务栏右键「退出」 | 窗口 `close` → `window-all-closed` → `app.quit()` → `before-quit` 收尾 | 这个窗口退出；**还有别的窗口在用则服务继续跑**，否则被 SIGTERM→SIGKILL 回收 |
| 应用菜单「退出」/ `Ctrl+Q` | 同上 | 同上 |
| 注销、关机、终端里 `kill <壳pid>`（SIGTERM/SIGINT/SIGHUP） | 信号处理 → `app.quit()` → `before-quit` 收尾 | 同上（**第一版漏的就是这条**） |
| 进程异常走到 `exit`（`before-quit` 没跑完） | `process.on('exit')` 同步补一刀 SIGKILL | 只有在自己是最后一个使用者时才补刀，否则原样保留服务 |
| `kill -9` / 崩溃（上面全都来不及） | 下次启动读 `~/.dsh-desktop/server.pid` 清理残留 | 残留服务被收掉，不用人工处理 |

「还有没有窗口在用」由 `~/.dsh-desktop/clients/<pid>.json` 这份登记表回答：
每个壳启动时登记自己、退出时删掉，退出前数一数还剩几个。

`~/.dsh-desktop/server.pid` 里记的是「服务器 pid + 起它的壳 pid + 完整命令行 + 启动时间」。
它有两个用途：清理上次的残留；以及让**最后一个退出的窗口**能停掉一台不是自己起的服务器。
下次启动清理残留时有四道闸门，缺一不可，原则是**宁可漏清、绝不误杀**：

1. 记录的进程还活着；
2. 它的命令行确实是本程序起的 `dsh web ... --no-open ...`（排除 pid 被系统复用）；
3. 记录里起它的那个壳已经不在了；
4. **登记表里没有别的活着的窗口**（有窗口在用时，那台服务器绝不能碰）。

所以你在终端里手动跑的 `dsh web` 永远不会被这个机制误伤。

## 三、安装与使用

```bash
cd dsh-desktop                   # 你克隆本仓库得到的目录
npm install                      # 未安装依赖时才需要执行
bash tools/install-launcher.sh   # 生成图标 + 注册应用 + 在桌面放启动图标
```

装完后有三种启动方式：

- 应用列表搜 `DSH`；
- 双击桌面上的「DSH 桌面版」图标；
- 命令行：`./bin/dsh-desktop`

窗口操作：

| 操作 | 效果 |
| --- | --- |
| 点窗口 × | 退出这个窗口；还有别的窗口在用后台服务时服务继续跑，最后一个窗口退出时才回收 |
| `Ctrl+Q` / 应用菜单「退出」 | 同上 |
| 应用菜单 `DSH` | 显示窗口、在浏览器打开当前地址、重启服务器、查看服务器日志、打开数据目录 |

日志与状态文件都在 `~/.dsh-desktop/`：

- `app.log`：桌面壳自己的日志（启动顺序、窗口事件、退出流程、退出判定）；
- `dsh-server.log`：`dsh web` 的原始输出 + 服务器生命周期（启动、停止、残留清理），
  也就是应用菜单「查看服务器日志」打开的那份；
- `server.pid`：当前托管服务器的 pid 记录（正常退出会删掉，留着就说明上次是被硬杀的）；
- `endpoint.json`：运行中服务器的访问地址公告（含 token，0600 权限），供后续窗口复用；
- `clients/`：谁正在使用后台服务的登记表（每个窗口一个 `<pid>.json`）；
- `window-state.json`：窗口大小与位置记忆。

> 数据目录可以用环境变量 `DSH_DESKTOP_APP_DIR` 覆盖（端到端测试靠它做隔离）；
> `DSH_DESKTOP_DSH_BIN` 可以指定用哪个 `dsh` 可执行文件。

## 五、多窗口是怎么工作的

在两块屏上各开一个 DSH 窗口，靠的不是「起两个后台服务」，而是**复用同一个地址**：

```
第 1 次点图标 → 壳A 起 dsh web → 把地址 + 服务器 pid 写进 ~/.dsh-desktop/endpoint.json
第 2 次点图标 → 壳B 拿不到单实例锁 → 读到公告 → 直接加载同一个地址（自己不起服务）
```

几个必须知道的细节：

- **单实例锁失败不等于程序要退出**。Electron 的锁只是告诉应用「已经有一个壳在跑」，
  进程本身还会继续执行 —— 实测确认过。所以多开的关键是拿到 `false` 时不要 `quit()`，
  而是转去复用。早期版本正是在这里直接退出，才导致点第二次图标毫无反应。
- **锁是挂在 userData 目录上的**，两个壳共用 `~/.config/Dsh Desktop`，所以第二个壳必然是「未持锁」。
  测试脚本也刻意共用同一个 `--user-data-dir` 来复现这条真实路径。
- **会等，而不是抢**。第一个壳可能还在冷启动（十几秒）、公告还没写出来。
  第二个壳最多等 30 秒；等到了就接上，等不到才退回「自己起一个服务器」。
  这正是「点了没反应，再点一次」这个常见操作能正确工作的原因。
- **两个窗口各记各的位置**（`window-state.json` 与 `window-state.secondary.json`），
  否则每次打开都要重新拖窗口。
- **共享同一个后端有一个限制**：两个窗口同时打开**同一个会话**会互相干扰（都看不到对方的实时流）。
  建议 A 屏开项目 A 的会话、B 屏开项目 B 的会话，各干各的。

## 六、服务器的寿命：最后一个窗口退出才回收

这是第四版的核心规则，一句话：**服务器不属于任何窗口，它属于「当前打开着的这些窗口」**。

```
每个壳启动 → 写 clients/<pid>.json（登记「我在用」）
每个壳退出 → 先删掉自己的登记，再数还剩几个：
     还剩 ≥ 1 个 → 服务器进程、地址公告、server.pid 记录，一律不动
     剩 0 个     → 先撤公告，再停服务器
                    · 服务是自己起的   → 停子进程（按进程组 SIGTERM → SIGKILL）
                    · 服务是别人起的   → 按 server.pid 记录核对身份后停掉（副本也能关灯）
```

由此得到的实际行为：

| 操作 | 后台服务 | 说明 |
| --- | --- | --- |
| 关掉副窗口（主窗口还在） | 继续跑 | 一直是这个行为 |
| **关掉主窗口（副窗口还在）** | **继续跑** | 第四版修的；副窗口无缝继续用，新开的窗口也还能接上 |
| 关掉最后一个窗口 | 回收 | 撤公告 + 停进程组，不留残留 |
| 最后一个窗口被 `kill -9` | 下次启动时回收 | 壳没机会收尾，靠 `server.pid` 兜底清理 |

三个容易踩的点，代码里都做了防护：

- **判断「还有没有窗口在用」要排除自己**，否则每个窗口都以为「还有别人」，服务器再也回收不掉。
- **一个窗口会被算成好几个进程**。Electron 主进程之外还有 zygote / GPU / 渲染进程，命令行里都带
  Electron 路径；只按「命令行含 electron」判断会把一个窗口数成四个，所以必须排除 `--type=` 的子进程。
- **登记表会被死 pid 污染**（壳被 `kill -9` 时来不及注销）。读取时会过滤死 pid 并顺手清理，
  而且还要核对命令行身份 —— 否则一个被系统复用的 pid 会让「死窗口」看起来一直活着。
- **服务器的输出不能再接壳的管道**。管道会在壳退出时断裂，服务器下一次写 stdout 就会拿到
  未处理的 EPIPE 而直接结束进程 —— 那样「主窗口关了服务还在」只会维持到它下次打日志为止。
  所以第四版起 stdout/stderr 直接写 `dsh-server.log`，就绪地址也从那个文件里读。

## 七、验证

```bash
# 单元自测（全部秒级完成，不需要图形界面）
node tools/endpoint-selftest.js     # 地址公告板（15 项）
node tools/clients-selftest.js      # 客户端登记表（11 项）
node tools/quit-flow-selftest.js    # 退出判定与回收（8 项，含竞态防护）

# 端到端（需要图形界面；全程隔离，不碰你正在用的桌面壳）
bash tools/e2e-owner-first-test.sh        # 先关主窗口（28 项，假 dsh，一分钟内）—— 第四版修复的那个问题
bash tools/e2e-multi-window-test.sh       # 多窗口与复用（22 项，假 dsh）
bash tools/e2e-close-test.sh              # 关闭语义三条路径（15 项）
bash tools/e2e-reuse-wait-test.sh         # 冷启动期间又点一次图标（13 项）
bash tools/e2e-real-multi-window-test.sh  # 真实 dsh 的多窗口 + 先关主窗口（21 项，约三分钟）
```

多窗口这几个脚本覆盖的断言包括：第二个壳确实「未持锁」、全程只起一个 `dsh` 服务、
X 服务器上真的出现了两个窗口、副窗口标题带「副窗口」标记、两个窗口状态文件互不覆盖、
`server.pid` 归属主壳、关掉副壳不动主服务、关掉最后一个窗口才回收服务并撤下公告。
`e2e-owner-first-test.sh` 专门验证反过来那条顺序：**关掉主窗口后服务、公告、pid 记录都还在**，
公告地址仍能访问，之后新开的第三个窗口仍复用同一台服务，直到最后一个窗口退出才回收。

它们全程在隔离环境里跑（`DSH_DESKTOP_APP_DIR` 指向 `/tmp` 下的独立目录、假 `dsh` 脚本、
独立 `--user-data-dir`），**不会碰到你正在用的那个桌面壳和它的服务器**。
真实 dsh 那个脚本还会另设一个空的 `DSH_HOME`，所以只加载最原始的 profile，不碰你的插件与凭据。

> 注意：测试窗口会短暂出现在当前桌面上，关闭时按**窗口 pid** 精确定位，
> 绝不用 `wmctrl -c <标题子串>` —— 历史上这么干误关过用户标题里含 “DeepSeek Harness” 的浏览器窗口。

## 八、两个 Linux 上的坑（已在代码里处理）

1. **`chrome-sandbox` 权限**：Electron 自带的沙箱辅助程序要求 `root:root` + `4755`，
   装在 `node_modules` 里天然不满足，直接启动会 FATAL 退出。
   启动脚本因此带上 `--no-sandbox`（`main.js` 里也做了一次探测兜底）。
   本程序只加载本机回环页面、不给渲染进程任何 Node 能力，风险可控。
   若想恢复 Chromium 沙箱，执行一次：

   ```bash
   sudo chown root:root node_modules/electron/dist/chrome-sandbox
   sudo chmod 4755 node_modules/electron/dist/chrome-sandbox
   ```

2. **从图标启动时 PATH 很干净**：图形会话的 PATH 里没有 npm 全局 bin 目录，
   直接 `spawn('dsh')` 会找不到命令。`bin/dsh-desktop` 负责把 npm 全局 bin 和 node 目录补进 PATH。

## 九、已知边界

- 多窗口共享同一个后端：两个窗口同时打开**同一个会话**会互相干扰，建议一个窗口一个会话。
- 桌面壳和你在终端里跑的 `dsh web` 是**两个独立进程**（各有一份会话运行态），
  但会话文件都落在 `~/.dsh/sessions`，两边都能看到历史记录。
  建议只保留一个入口，避免自己跟自己抢同一份工作区文件。
- 「关窗口就退出」意味着**误触 × 会中断正在跑的任务**。这是用户明确选择的行为
  （不要托盘、不要确认框）；需要长时间跑任务时请别关窗口。
  注意只有**最后一个**窗口关闭才会真正中断：只要还有别的窗口在用，后台服务（以及里面正在跑的任务）就继续活着。
- **副窗口不能重启服务器**（它的菜单里没有「重启服务器」）：重启会换端口、换 token，
  等于把其他窗口脚下的地板抽走。同理，主窗口关闭后，还活着的窗口标题仍然是「DSH（副窗口）」——
  功能完全正常（同一后端、同一会话、同一页面），只是不会「接管主身份」。
- **从主窗口点「重启服务器」时，副窗口仍会断**（端口与 token 都换了）。这条路径第四版没有改动，
  要修的话让副窗口在重新加载前重读一次公告即可。
- 被 `kill -9` 的残留服务器最迟会在**下次启动桌面壳**时被清掉；
  如果你希望「壳一死服务立刻跟着死」，需要在壳与服务器之间再插一个监护进程，
  目前没做（收益小于复杂度）。
- **升级期**：旧版壳不写客户端登记表，所以「旧版主窗口 + 新版副窗口」混跑时，旧版主窗口退出仍会把服务停掉。
  写完代码后把所有窗口关掉重开，新语义才完全生效。
- 窗口标题由本程序钉住（`page-title-updated` 里 `preventDefault`），
  所以不会显示网页自己的标题 —— 这是为了在两块屏上能区分「DSH」与「DSH（副窗口）」。
