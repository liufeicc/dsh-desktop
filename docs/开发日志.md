# DSH 桌面版 —— 开发日志

## 2026-10-10 第一版（Electron 托盘壳）

> 注意：本版「关闭 = 隐藏到托盘」的语义已被第二版废弃，见文末。

### 需求

用户的原话是：「dsh 是用浏览器打开的，我经常会误关浏览器，是否可以将 dsh 变成桌面程序？」
确认后的选择：直接做带托盘的桌面壳；**服务器由桌面程序自己拉起，退出时一并关掉**。

### 结论性的取舍

| 候选方案 | 结论 |
| --- | --- |
| Chrome `--app` 应用模式 + systemd 常驻 | 备选，但窗口仍可被关闭，用户明确否决 |
| 浏览器装成 PWA（dsh 自带 manifest，`display: fullscreen`） | 同样无法阻止误关，且全屏会盖住整个屏幕，体验反而更差 |
| nodegui / Neutralino / Tauri | 需要额外工具链或功能不全（托盘、单实例），成本高于收益 |
| **Electron 托盘壳（采用）** | 本地 `~/.cache/electron` 已有 v30.5.1 的 Linux 包，无需联网下载 100MB+；崩溃处理、托盘、单实例齐全 |

### 关键实现细节（踩过的坑）

1. **带 token 的地址只能从 stdout 抓**：dsh 网页端用「一次性 token 换 30 天签名 cookie」的机制，
   自己拼 `http://127.0.0.1:<port>` 会得到 401。服务器就绪时会打印
   `dsh web: http://.../?token=...`，桌面壳用正则解析这一行。
2. **端口用 0（系统分配）**：用户机器上常年跑着一个 3080 的 `dsh web`，固定端口会撞车。
3. **进程组回收**：子进程用 `detached: true` 自成进程组，停止时 `kill(-pid)`，
   否则 dsh 派生的 bash 等孙进程会变成孤儿。
4. **`chrome-sandbox` 需要 root:root + 4755**：普通用户安装的 `node_modules` 不满足，
   启动会 FATAL。启动脚本统一带 `--no-sandbox`，`main.js` 里再做一次权限探测兜底。
5. **从 `.desktop` 启动时 PATH 很干净**：必须在启动脚本里补 `~/.npm-global/bin` 与 node 目录。
6. **启动要 17~40 秒**：先加载本地过渡页给反馈，服务器就绪后再 `loadURL`。
   （第一版在 `startServer()` 里无条件再 `loadFile` 一次过渡页，导致
   `ERR_ABORTED (-3) loading 'file://.../loading.html'`；已改为只在「重启服务器」时切回过渡页。）
7. **`StartupWMClass` 必须写成 `Dsh Desktop`**：Electron 按 `app.setName()` 生成 WM_CLASS
   （实测 `dsh desktop` / `Dsh Desktop`），写 `dsh-desktop` 会让任务栏认不出这个应用。

### 事故记录（必须记住的教训）

测试「关闭窗口」时用了 `wmctrl -c "DeepSeek Harness"`。`wmctrl -c` 是**按标题子串匹配**，
结果把用户那扇标题里也含 “DeepSeek Harness” 的 Chrome 窗口关掉了，Chrome 因最后一个窗口关闭而整体退出。
已用 `google-chrome --restore-last-session` 恢复（会话 cookie 有效，页面正常回来）。

**规则：以后测试窗口关闭，一律用 `wmctrl -i -c <十六进制窗口id>` 精确指定，绝不用标题子串匹配。**

### 后续可选增强

- 开机自启（`~/.config/autostart/dsh-desktop.desktop`，加 `X-GNOME-Autostart-enabled=true`）；
- 把服务器改成 systemd 用户服务常驻，桌面壳只当窗口（换回「服务器不随窗口退出」的形态）；
- 托盘菜单加「新建会话」「切换工作区」等快捷项（需要走 dsh 的接口，属于较大改动）。

## 2026-10-10 第二版（关窗口 = 退出程序 = 停掉后台服务）

### 需求

用户原话：「现在发现 DEEPSEEK HARNESS 壳在关闭时，后台服务并没有关闭，应该一并关闭。」
追问确认后的选择：**点 × 直接彻底退出，不弹确认框，也不保留「隐藏到托盘」**（关就是关）。

### 问题定位：先看证据，再动代码

改之前先把 `~/.dsh-desktop/` 两份日志和 `ps` 摆出来看，结论和第一版的假设不一样：

| 时刻（UTC） | 日志 | 说明 |
| --- | --- | --- |
| 02:17:32 | `窗口已隐藏到托盘` | 用户点了 ×，第一版把它拦成了隐藏 |
| 02:18:30 | `服务器进程退出 signal=SIGKILL expected=false` | 用户自己去命令行把还在跑的服务器 `kill -9` 了 |
| 02:18:33 | `开始退出流程` | 壳弹出「服务器已停止」对话框后，用户才选「退出程序」 |
| 02:45:36 | `服务器进程退出 code=0 signal=null expected=false` | 又一次外部 kill（`pkill` 之类），之后用户选了「重启服务器」 |

所以问题**不是**「退出流程没杀干净」（`00:44:06`、`00:49:01` 两次 `Ctrl+Q` 都规规矩矩发了 SIGTERM），
而是 **× 的语义本身就是「隐藏」**，服务按设计继续跑 —— 用户不认这个设计。
顺带查出一个真实漏洞：子进程 `detached: true` 自成进程组，壳被 `kill -9`／崩溃／注销时来不及走
`before-quit`，`dsh web` 会被 init 收养变成永久孤儿；`main.js` 里也没有监听 `SIGTERM/SIGINT`。

### 方案：四条退出路径 + 一层兜底

| 触发方式 | 走哪条路 |
| --- | --- |
| 点 ×／Alt+F4／任务栏右键「退出」 | 窗口 `close` → `window-all-closed` → `app.quit()` → `before-quit` 收尾 |
| 应用菜单「退出」／`Ctrl+Q` | `app.quit()` → 同上 |
| 注销／关机／`kill <壳pid>`（SIGTERM/SIGINT/SIGHUP） | 信号处理 → `app.quit()` → 同上 |
| 异常直接走到 `exit` | `process.on('exit')` 同步 SIGKILL |
| `kill -9`／崩溃（上面全都来不及） | 下次启动读 `server.pid` 清理残留 |

残留清理的三道闸门（宁可漏清、绝不误杀）：① 记录的进程还活着；② 命令行确实是本程序起的
`dsh web … --no-open …`（排除 pid 复用）；③ 记录里的壳进程已经不在（壳还在就说明是它在用，不能碰）。
这样用户在终端里手动跑的 `dsh web` 不会被误伤。

### 实现要点

- `main.js`：删掉 `close` 拦截、`Tray`、`Notification`；`window-all-closed → app.quit()`；
  `before-quit` 里用 `quitRequested`/`quitReady` 双标记防重入，并加 12 s 强退兜底（窗口不能被卡住关不掉）；
  监听 SIGTERM/SIGINT/SIGHUP；`process.on('exit')` 补最后一刀；原来托盘菜单里的功能整体挪进应用菜单。
- `lib/server.js`：新增 `pidFile` 记录（`pid + shellPid + command + startedAt`）、`onSpawn` 回调、
  `reapStaleServer()`；`start()` 改 `async`，spawn 之前先把上一任的残留清掉。
- `main.js` 退出事件里区分「用户正在退出」和「服务器真崩了」，退出过程中的启动失败不再弹错误框。
- 去掉托盘图标（`tools/make-icons.py`、`assets/tray*.png`）、更新 `.desktop` 文案、README、package.json。

### 验证记录

新增 `tools/e2e-close-test.sh`：全程隔离（`DSH_DESKTOP_APP_DIR` 指向 `/tmp`、假 `dsh` 脚本、
独立 `--user-data-dir`），**不碰用户正在使用的那个壳和它的服务器**。

| 场景 | 断言 | 结果 |
| --- | --- | --- |
| 点窗口 ×（`wmctrl -i -c <窗口id>`） | 壳退出、后台服务消失、`server.pid` 被清理 | 通过 |
| 给壳发 SIGTERM | 壳退出、后台服务消失 | 通过 |
| `kill -9` 硬杀壳 | 复现原问题（服务仍在跑）；重启壳后残留被清掉、起了新服务器、日志有清理记录 | 通过 |

合计 15 项断言全绿。真实实例（壳 pid 96585、服务器 113046，端口 43143）全程未被触碰。

### 遗留 / 取舍

- 「关就是关」意味着**误触 × 会中断正在跑的任务**，这是用户明确选的（不要托盘、不要确认框），
  已写进 README 的「已知边界」。
- 被 `kill -9` 的残留最迟在**下次启动壳**时被清掉。要做到「壳一死服务立刻死」，
  需要在壳与服务器之间插一个监护进程（用 IPC 生命线检测父进程消失），当前判断收益小于复杂度，没做。
- 应用图标脚本依赖 `cairosvg`，本机 python3 环境目前没装（图标是更早生成的，本次只删了托盘图标那两行，
  没有重新生成图标）。
