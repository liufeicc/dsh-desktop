# DSH 桌面版 —— 开发日志

## 2026-10-10 第一版（Electron 托盘壳）

> 注意：本版「关闭 = 隐藏到托盘」的语义已被第二版废弃，见文末。

### 需求

用户的原话是：「dsh 是用浏览器打开的，我经常会误关浏览器，是否可以将 dsh 变成桌面程序？」
确认后的选择：直接做带托盘的桌面壳；**服务器由桌面程序自己拉起，退出时一并关掉**。

### 结论性的取舍

| 候选方案 | 结论 |
| --- | --- |
| Chrome `--app` 应用模式 + systemd 常驻 | 备选，但窗口仍可被关闭，用户明确否决 |
| 浏览器装成 PWA（dsh 自带 manifest，`display: fullscreen`） | 同样无法阻止误关，且全屏会盖住整个屏幕，体验反而更差 |
| nodegui / Neutralino / Tauri | 需要额外工具链或功能不全（托盘、单实例），成本高于收益 |
| **Electron 托盘壳（采用）** | 本地 `~/.cache/electron` 已有 v30.5.1 的 Linux 包，无需联网下载 100MB+；崩溃处理、托盘、单实例齐全 |

### 关键实现细节（踩过的坑）

1. **带 token 的地址只能从 stdout 抓**：dsh 网页端用「一次性 token 换 30 天签名 cookie」的机制，
   自己拼 `http://127.0.0.1:<port>` 会得到 401。服务器就绪时会打印
   `dsh web: http://.../?token=...`，桌面壳用正则解析这一行。
2. **端口用 0（系统分配）**：用户机器上常年跑着一个 3080 的 `dsh web`，固定端口会撞车。
3. **进程组回收**：子进程用 `detached: true` 自成进程组，停止时 `kill(-pid)`，
   否则 dsh 派生的 bash 等孙进程会变成孤儿。
4. **`chrome-sandbox` 需要 root:root + 4755**：普通用户安装的 `node_modules` 不满足，
   启动会 FATAL。启动脚本统一带 `--no-sandbox`，`main.js` 里再做一次权限探测兜底。
5. **从 `.desktop` 启动时 PATH 很干净**：必须在启动脚本里补 `~/.npm-global/bin` 与 node 目录。
6. **启动要 17~40 秒**：先加载本地过渡页给反馈，服务器就绪后再 `loadURL`。
   （第一版在 `startServer()` 里无条件再 `loadFile` 一次过渡页，导致
   `ERR_ABORTED (-3) loading 'file://.../loading.html'`；已改为只在「重启服务器」时切回过渡页。）
7. **`StartupWMClass` 必须写成 `Dsh Desktop`**：Electron 按 `app.setName()` 生成 WM_CLASS
   （实测 `dsh desktop` / `Dsh Desktop`），写 `dsh-desktop` 会让任务栏认不出这个应用。

### 事故记录（必须记住的教训）

测试「关闭窗口」时用了 `wmctrl -c "DeepSeek Harness"`。`wmctrl -c` 是**按标题子串匹配**，
结果把用户那扇标题里也含 “DeepSeek Harness” 的 Chrome 窗口关掉了，Chrome 因最后一个窗口关闭而整体退出。
已用 `google-chrome --restore-last-session` 恢复（会话 cookie 有效，页面正常回来）。

**规则：以后测试窗口关闭，一律用 `wmctrl -i -c <十六进制窗口id>` 精确指定，绝不用标题子串匹配。**

### 后续可选增强

- 开机自启（`~/.config/autostart/dsh-desktop.desktop`，加 `X-GNOME-Autostart-enabled=true`）；
- 把服务器改成 systemd 用户服务常驻，桌面壳只当窗口（换回「服务器不随窗口退出」的形态）；
- 托盘菜单加「新建会话」「切换工作区」等快捷项（需要走 dsh 的接口，属于较大改动）。

## 2026-10-10 第二版（关窗口 = 退出程序 = 停掉后台服务）

### 需求

用户原话：「现在发现 DEEPSEEK HARNESS 壳在关闭时，后台服务并没有关闭，应该一并关闭。」
追问确认后的选择：**点 × 直接彻底退出，不弹确认框，也不保留「隐藏到托盘」**（关就是关）。

### 问题定位：先看证据，再动代码

改之前先把 `~/.dsh-desktop/` 两份日志和 `ps` 摆出来看，结论和第一版的假设不一样：

| 时刻（UTC） | 日志 | 说明 |
| --- | --- | --- |
| 02:17:32 | `窗口已隐藏到托盘` | 用户点了 ×，第一版把它拦成了隐藏 |
| 02:18:30 | `服务器进程退出 signal=SIGKILL expected=false` | 用户自己去命令行把还在跑的服务器 `kill -9` 了 |
| 02:18:33 | `开始退出流程` | 壳弹出「服务器已停止」对话框后，用户才选「退出程序」 |
| 02:45:36 | `服务器进程退出 code=0 signal=null expected=false` | 又一次外部 kill（`pkill` 之类），之后用户选了「重启服务器」 |

所以问题**不是**「退出流程没杀干净」（`00:44:06`、`00:49:01` 两次 `Ctrl+Q` 都规规矩矩发了 SIGTERM），
而是 **× 的语义本身就是「隐藏」**，服务按设计继续跑 —— 用户不认这个设计。
顺带查出一个真实漏洞：子进程 `detached: true` 自成进程组，壳被 `kill -9`／崩溃／注销时来不及走
`before-quit`，`dsh web` 会被 init 收养变成永久孤儿；`main.js` 里也没有监听 `SIGTERM/SIGINT`。

### 方案：四条退出路径 + 一层兜底

| 触发方式 | 走哪条路 |
| --- | --- |
| 点 ×／Alt+F4／任务栏右键「退出」 | 窗口 `close` → `window-all-closed` → `app.quit()` → `before-quit` 收尾 |
| 应用菜单「退出」／`Ctrl+Q` | `app.quit()` → 同上 |
| 注销／关机／`kill <壳pid>`（SIGTERM/SIGINT/SIGHUP） | 信号处理 → `app.quit()` → 同上 |
| 异常直接走到 `exit` | `process.on('exit')` 同步 SIGKILL |
| `kill -9`／崩溃（上面全都来不及） | 下次启动读 `server.pid` 清理残留 |

残留清理的三道闸门（宁可漏清、绝不误杀）：① 记录的进程还活着；② 命令行确实是本程序起的
`dsh web … --no-open …`（排除 pid 复用）；③ 记录里的壳进程已经不在（壳还在就说明是它在用，不能碰）。
这样用户在终端里手动跑的 `dsh web` 不会被误伤。

### 实现要点

- `main.js`：删掉 `close` 拦截、`Tray`、`Notification`；`window-all-closed → app.quit()`；
  `before-quit` 里用 `quitRequested`/`quitReady` 双标记防重入，并加 12 s 强退兜底（窗口不能被卡住关不掉）；
  监听 SIGTERM/SIGINT/SIGHUP；`process.on('exit')` 补最后一刀；原来托盘菜单里的功能整体挪进应用菜单。
- `lib/server.js`：新增 `pidFile` 记录（`pid + shellPid + command + startedAt`）、`onSpawn` 回调、
  `reapStaleServer()`；`start()` 改 `async`，spawn 之前先把上一任的残留清掉。
- `main.js` 退出事件里区分「用户正在退出」和「服务器真崩了」，退出过程中的启动失败不再弹错误框。
- 去掉托盘图标（`tools/make-icons.py`、`assets/tray*.png`）、更新 `.desktop` 文案、README、package.json。

### 验证记录

新增 `tools/e2e-close-test.sh`：全程隔离（`DSH_DESKTOP_APP_DIR` 指向 `/tmp`、假 `dsh` 脚本、
独立 `--user-data-dir`），**不碰用户正在使用的那个壳和它的服务器**。

| 场景 | 断言 | 结果 |
| --- | --- | --- |
| 点窗口 ×（`wmctrl -i -c <窗口id>`） | 壳退出、后台服务消失、`server.pid` 被清理 | 通过 |
| 给壳发 SIGTERM | 壳退出、后台服务消失 | 通过 |
| `kill -9` 硬杀壳 | 复现原问题（服务仍在跑）；重启壳后残留被清掉、起了新服务器、日志有清理记录 | 通过 |

合计 15 项断言全绿。真实实例（壳 pid 96585、服务器 113046，端口 43143）全程未被触碰。

### 事故记录：一个差点让本次修复「看着对、过一会儿失效」的坑

方案写完之后、动手实跑之前，先单独验证了一个前提：**服务器进程的 stdout/stderr 是接在壳上的管道**，
壳退出时管道会断 —— 那么服务器之后往 stdout 写东西会怎样？

实验（用 `node -e` 造一个 detached 子进程，stdout 接管道并持续写，父进程 1.5 秒后退出）：

| 子进程有没有 `uncaughtException` 处理器 | 结果 |
| --- | --- |
| 有（把 EPIPE 吞掉） | 一直活着，但每次写都抛一次 EPIPE |
| **没有（像真实 `dsh web` 那样裸写）** | **当场死亡**：心跳停在父进程退出的那一刻 |

也就是说：即便生命周期判定完全正确，只要后台服务以后往 stdout 打一行日志（一个警告、一次报错），
它就会因未处理的 EPIPE 结束进程，副窗口照样断连 —— 而且这种故障「刚关主窗口时一切正常、几十秒后才炸」，
极难排查。

所以把输出载体一并换掉：**spawn 时让 stdout/stderr 直接指向 `dsh-server.log`（追加模式），
就绪地址改成「读这个文件」取得**。附带三个好处：服务器输出由它自己落盘（不再经壳转发）、
日志里不再每行出现两份、壳退出后服务器与壳之间不存在任何管道。
`tools/e2e-owner-first-test.sh` 里专门留了一条回归断言：假 dsh 持续写 stdout/stderr，
壳退出后心跳次数必须继续增长。

### 代码拆分（本次顺手做的，别当成无关紧要）

改完这一版，`main.js` 到了 966 行 —— 既超出仓库约定的「单文件不超过 800 行」，
也说明它把「Electron 接线」和「服务器生命周期语义」混在了一起。于是拆出三个模块：

| 新模块 | 承担什么 | 为什么值得单独放 |
| --- | --- | --- |
| `lib/quit-flow.js` | 退出判定与收尾 | 这是最容易改错、也最需要被反复阅读的一段；拆出来之后还能脱离 Electron 做单元测试（`tools/quit-flow-selftest.js`） |
| `lib/window-state.js` | 窗口几何记忆 | 主/副窗口各一份的读写规则集中一处，`main.js` 只剩一行调用 |
| `lib/menu.js` | 应用菜单 | 菜单项随窗口模式变化（副窗口不能重启服务器），这段分支逻辑集中放更清楚 |

拆完 `main.js` 788 行，其余模块都在 200 行上下。

拆的过程中被自己的自测抓到一次**测试前提错误**，值得记一笔：
「停止期间 pid 记录被新壳改写」这条断言一开始失败，看起来像实现漏了竞态防护。
实际原因是测试在假 dsh **还没启动完**（SIGTERM 处理器尚未注册）时就发了信号 ——
默认动作直接杀掉进程，处理器根本没跑，文件自然没被改写。
真实场景里服务器早就起好了，不存在这个问题，但测试必须显式等它就绪。

### 遗留 / 取舍

- 「关就是关」意味着**误触 × 会中断正在跑的任务**，这是用户明确选的（不要托盘、不要确认框），
  已写进 README 的「已知边界」。
- 被 `kill -9` 的残留最迟在**下次启动壳**时被清掉。要做到「壳一死服务立刻死」，
  需要在壳与服务器之间插一个监护进程（用 IPC 生命线检测父进程消失），当前判断收益小于复杂度，没做。
- 应用图标脚本依赖 `cairosvg`，本机 python3 环境目前没装（图标是更早生成的，本次只删了托盘图标那两行，
  没有重新生成图标）。

## 2026-10-14 第三版（多窗口：两块屏上各开一个）

### 需求

用户有两块屏幕，希望两个屏幕上都操作 DSH。当前行为是「第二次点图标只把已有窗口叫到前台」，
因为 `app.requestSingleInstanceLock()` 拿不到锁就直接退出了。

用户自己的描述是：**「dsh-desktop 只是一个壳，访问的是一个 url 进行显示，应该像开两个浏览器窗口访问一个地址一样」**。
这个心智模型是对的，而且指向了最省的实现：不是起两个后端，而是两个窗口看同一个地址。

### 先说结论：四条实测证据

动手前把前提一条条验掉，避免在错误假设上写代码：

| 验证项 | 结论 | 怎么验的 |
| --- | --- | --- |
| `/api/remote.mux` 支不支持多客户端 | **支持**，每次 upgrade 独立 admit 成一个 Peer，各自开独立 stream | 用同一个 cookie 开两条 WebSocket，2.5 秒后都是 OPEN |
| 同一 token 能不能重复换 cookie | **能**，连换 3 次都返回 303 | curl 三次看 `set-cookie` |
| 单实例锁失败会不会杀掉进程 | **不会**。拿不到锁后代码照常往下跑，退不退出由应用自己决定 | 最小 Electron 程序打印 `requestSingleInstanceLock()` 前后，两个进程都跑完了 |
| 锁挂在哪个目录上 | **userData**。共用 `--user-data-dir` 才拿不到锁，各用各的则都能拿到 | 两组对照实验 |

第三条最关键：**多开的关键不是绕开锁，而是拿到 `false` 时不要 quit**。

### 方案

```
第 1 个壳：起自己的 dsh web → 把地址写进 ~/.dsh-desktop/endpoint.json（0600 权限，含 token）
后续的壳：拿不到锁 → 读公告 → 直接加载同一个地址，自己不起服务
```

新增 `lib/endpoint.js` 负责这个公告板，失效判断三道：文件读不出、写公告的壳已退出、地址不是 http(s)。
不做 HTTP 探活——`shellPid` 存活检查已经覆盖绝大多数情况，探活只会拖慢启动。

`main.js` 的改动集中在一处核心问题：**模式必须在建窗口之前定下来**。
菜单、窗口标题、窗口几何状态文件都按模式分两套，建好了再改就会出现「菜单是主窗口的、窗口是副窗口的」这种错配。
所以 `boot()` 的顺序是：定模式 → 建菜单与窗口 → 接服务器或起服务器。

### 实现要点（都是实际踩出来的）

1. **必须等，不能看一眼就决定**。单实例锁只说明「有个壳在跑」，那个壳可能还在冷启动（十几秒），公告还没写出来。
   用户真实节奏恰恰是「点了没反应，再点一次」。第二个壳最多等 30 秒，等不到才退回自起服务。
   为此加了 `tools/e2e-reuse-wait-test.sh` 专门验证这条路径。
2. **`server.port` 不是实际端口**。构造时传的是 `0`（让系统挑），`this.port` 一直保持 0，真实端口只在就绪地址里。
   公告里的 port 必须从 URL 解析，否则记的是 0。
3. **`loadFile()` 被打断会 reject，且这是正常流程**。启动时先摆过渡页、服务器就绪后再 `loadURL` 换成真页面，
   过渡页那次加载必然以 `ERR_ABORTED (-3)` 失败。这属于正常流程，不该记成失败日志
   （否则真正的加载失败会被噪音淹没）。加了 `isNavigationSuperseded()` 专门识别它。
4. **复用模式要跳过过渡页**。地址是现成的，先摆过渡页只会让导航立刻被打断；而且此时窗口还没加载任何内容，
   所以改成一建好就隐藏、`loadURL` 成功后再 `showMainWindow()`，避免用户看到一块空白背景。
5. **窗口标题会被页面顶掉**。dsh 网页端加载完会设置 `document.title`，实测窗口标题会变成「DeepSeek Harness」，
   把 `BrowserWindow` 的 title 覆盖掉。两块屏上就再也分不清谁是谁了。
   解决办法是在 `page-title-updated` 里 `preventDefault()`，把标题钉成「DSH」/「DSH（副窗口）」。
6. **副窗口的菜单不能有「重启服务器」**。那个按钮会另起一个属于副壳自己的服务（与主实例抢端口、也让用户困惑），
   换成「重新加载界面」；退出菜单也写明「服务器由主窗口继续运行」。
7. **窗口没被动过时几何信息会丢**。`resize`/`move`/`close` 都要用户动过窗口或走到关闭流程才触发，
   首次打开就被 `kill -9` 的话位置记不下来。改成 `ready-to-show` 时先写一次。

### 测试脚本本身的两个坑（比产品代码更值得记）

1. **同步条件不能用会提前命中的字符串**。我一开始用 `grep -q '复用已有实例的服务器'` 作为「等第二个壳接上」的条件，
   但锁失败那行日志里也含这几个字（「本次启动将复用已有实例的服务器（不是错误…）」），
   于是条件在第一毫秒就成立，断言跑在了壳B 真正接上之前（26s vs 38s），一直误报失败。
   改用只有真正接上时才打印的短语「本窗口不再启动服务器」。
   **教训：用日志做同步时，先确认这个字符串是这条路径独有的。**
2. **不要用固定 `sleep` 卡时间窗，也不要用 shell 的 `$SECONDS` 做时序判断**。两者一旦错位，
   断言会在「逻辑其实正确」的情况下误报。改成从日志内容推导（把等待时长从日志里读出来比对）。

### 遗留 / 取舍

- **两个窗口同时打开同一个会话会互相干扰**（都看不到对方的实时流）。这是共享后端的固有限制，
  已写进 README 的已知边界，建议一个窗口一个会话。
- 公告文件里带访问 token，用 0600 权限保护。同机其他用户读不到；同用户下本来也读得到 DSH_HOME 里的凭据，
  所以没有额外暴露面。
- 副窗口关闭不影响服务器（服务器属于主窗口）；主窗口关闭时副窗口会断连——这是「同一个地址」的必然结果，
  符合用户「像两个浏览器窗口」的心智模型。
  **（第四版已推翻这条判断，见下：同一个地址不等于同一条命，共享后端与共享生命周期是两件事。）**
- 主实例异常退出、锁已释放但公告还在时，抢到锁的壳会改用复用模式接上它（省一个 node 进程）。
  这条路径很罕见，代码里保留了日志便于排查。


## 2026-10-15 第四版（服务器寿命：最后一个窗口退出才停）

### 需求

用户原话：

> 现在 DSH 桌面版可以启动多个，有一个是主的，其他是副本，连接同一个后台服务。问题是如果我关闭了主的，
> 后台服务就被关闭了，副本就不能用了。我觉得应该是主的关闭了，后台服务不要关闭。
> 只有等所有启动的 DSH 桌面版都关闭了，才关闭后台服务。

### 问题定位：先看证据

在用户机器上抓到的现场（正好复现）：

| 角色 | pid | 说明 |
| --- | --- | --- |
| 主壳（Electron） | 6230 | 第一个启动，spawn 了后台服务 |
| 后台服务 | 6361 | `node .../dsh web --no-open --port 0`，`detached` 自成进程组，父进程 = 6230 |
| 副壳（Electron） | 91068 | 读 `endpoint.json` 复用 35003 这个地址 |

三条根因（都不是手误，是当时的有意取舍）：

1. `main.js` 的 `before-quit` 里**无条件** `stopServer()` —— 主壳把自己的子进程当成了「我的服务」；
2. `lib/endpoint.js` 判断公告还能不能用，依据是**「写公告的壳还活着吗」**（`shellPid`）——
   把「服务器可用」绑死在主壳身上。副作用是主壳一退，公告立刻失效，新开的窗口还会以为没人服务而**再起一台**；
3. 副壳**没有关灯的能力**：它既没有子进程句柄，代码里也没有任何路径去使用 `server.pid` 记录。

第三版文档里其实写过一句「主窗口关闭时副窗口会断连——这是同一个地址的必然结果」。
**这句判断是错的**：同一个地址 ≠ 同一条命。共享后端是设计目标，共享生命周期只是当时的实现方式。

### 方案

心智模型换成一句话：**服务器不属于任何窗口，它属于「当前打开着的这些窗口」**。

```
每个壳启动：写 clients/<pid>.json （登记「我在用」）
每个壳退出：先删掉自己的登记 → 再数还剩几个
    还剩 ≥ 1 → 服务器进程、地址公告、server.pid 记录一律不动
    剩 0     → 先撤公告，再停服务器
                  · 自己起的 → 停子进程（原路径）
                  · 不是自己起的 → 按 server.pid 记录核对身份后停进程组（新增，副本也能关灯）
```

跟着换掉的三个判据（少换一个都会出事）：

| 位置 | 旧判据 | 新判据 | 不换会怎样 |
| --- | --- | --- | --- |
| `lib/endpoint.js` 公告可用性 | 写公告的壳还活着 | **公告里的服务器进程还活着** | 主壳退出后公告失效，新窗口会再起一台服务 |
| `lib/server.js` 启动残留清理 | 起它的壳还活着 | **还有没有别的活壳** | 主壳退出后留下的服务被下一个壳当残留杀掉 |
| `main.js` 退出流程 | 我是主实例就停服务 | **我是最后一个使用者才停服务** | 就是用户报的这个 bug |

关键细节：**要停哪台服务器，在决策时读一次 pid 记录就锁定，之后不再重读文件**。
因为停止流程要等 SIGTERM 宽限期（最多 6 秒），中途重读可能读到新壳刚写进去的记录，
把别人刚起的服务器杀掉。

### 实现要点（坑都是实际踩出来的）

1. **登记表用「一个壳一个文件」，不用一份 JSON 名单**。一份 JSON 要跨进程读-改-写，
   两个壳同时启动/退出就会互相覆盖，还得引锁。一个 pid 一个文件则各写各的，天然无竞争。
2. **判断「壳还活着」必须过命令行身份核对**。pid 会被系统复用：壳崩溃后留下的登记文件，
   过一阵子可能被无关进程占用同一个 pid，光看「pid 存在」就会以为那个壳还在。
   核对方式是「命令行含 electron 且不含 `--type=`」（排除 Electron 的渲染/GPU/工具子进程）。
3. **读不到命令行时按「活着」算**。判错两个方向的代价不对称：
   把活着的壳漏掉 → 服务器被提前回收，别人正在看的窗口当场失效（严重）；
   把死掉的壳多算一个 → 只是晚一点回收（轻微，下次启动兜底清理）。
4. **数「还有几个」时一定要排除自己**。顺序还必须对：先把「是否最后一个」算出来，
   再动手。忘了排除自己的话，永远「还有别人在用」，服务器再也回收不掉。
5. **一个窗口会被算成 4 个进程**。Electron 主进程 + zygote + GPU + 渲染进程的命令行里都带 Electron
   可执行文件路径和应用路径。不排除 `--type=` 的话，「还有几个窗口在用」永远大于 1。
6. **撤公告改成无条件删除**。旧版带「属主核对」（只有写公告的壳才能删），于是
   「主壳先退、副壳最后退」时公告会残留下来，指向一台已经被停掉的服务。
7. **`process.on('exit')` 兜底要走同一套判据**。它是 kill -9 之外的最后一层；
   如果它仍旧按「我是主实例」补刀，就会把「主壳退出、副本还在用」的服务又杀掉一次。
   同时它只对决策时锁定的目标动手，不重读文件。
8. **兼容旧版公告**：没有 `serverPid` 字段的公告回退到旧的 `shellPid` 判据。
   否则升级期间「新壳 + 旧壳同时跑」时，新壳会判定没有可用服务，还顺手把旧壳正在用的那台当残留清掉。
9. **菜单文案不再分主/副**。旧文案「退出（会一并停掉后台服务）」「退出本窗口（服务器由主窗口继续运行）」
   在新语义下都是错的，统一改成「退出（最后一个窗口退出时才停后台服务）」。

### 遗留 / 取舍

- **副本仍然没有「重启服务器」**。它的服务器是别人的，重启会换端口、把别的窗口甩掉，所以菜单里不提供。
  主壳退出后，活着的窗口标题仍是「DSH（副窗口）」—— 功能完全正常（同一后端、同一会话、同一页面），
  只是没有「接管主身份」。要做接管是另一件事（改标题/菜单 + 让幸存窗口持有服务器句柄），本次没做。
- **主壳点「重启服务器」时，副本窗口仍会断**。这条路径第四版没动（一直存在）：
  新服务是新端口、新 token，副窗口还指着旧地址。要修的话，让副窗口在重新加载前重读一次公告即可。
- **同一会话在两个窗口里同时打开会互相干扰**（第三版遗留，共享后端的固有限制）。
- **升级期行为**：旧版壳不写登记表，所以「旧版主壳 + 新版副壳」混跑时，旧版主壳退出仍会把服务停掉。
  写完代码后需要把所有窗口关掉重开，新语义才完全生效。
